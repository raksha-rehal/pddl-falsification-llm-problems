## Part 1 — Project background

### Problem Statement

The problem I will investigate is how current AI technology can be used to test and improve the safety and navigation capacities of autonomous agents on lunar surfaces. These agents must handle and recover from surface anomalies such as displaced objects, loss of power or communication, etc. This work is important as failures on lunar surfaces are costly and difficult to test for. Automated planning and LLMs are powerful tools that will allow us to simulate and explore failure scenarios in advance. My work is novel as I will be studying how these agents fail, compared to work in the literature that has studied when these failures occur. My contributions will include a benchmark of LLM-generated failure scenarios, built by perturbing problem files of an existing planetary rover domain (the IPC-3 Rovers domain [4]), which serves as a proxy for an autonomous lunar agent. In this project, anomalies are injected into the problem files (the initial state), not into the domain. A lunar planning domain with tailored anomalies is left as future work.

**RQ1:** Given an existing PDDL domain that models the actions of an autonomous planetary rover, can LLMs generate perturbed problem files whose plans reach valid, non-trivial failure states?

**RQ2:** Is there an underlying pattern of perturbation features that LLMs followed to cause failures, and if so, which PDDL problem-file instantiations (i.e., initial-state configurations) should therefore be avoided or planned for?

> Use the RQ wording above exactly. Do not reword the RQs.

### Dataset

The datasets detailed below are publicly available, and can be collected via a simple script.

**Domain:** The IPC-3 Rovers PDDL domain [4], used as-is with no lunar actions or anomaly predicates added. Use the numeric version, which models rover energy (`energy`, a `recharge` action, and `in_sun` waypoints), so that power-loss anomalies can be expressed.

**Nominal problem files:** The IPC-3 Rovers problem files for the same domain version [4]. Each nominal problem file is paired with a nominal plan generated by a planner (see Planned Approach). Start with the smaller problem instances.

**Generated data:** The perturbed problem files produced by the LLM(s), together with their VAL results. Together these form the benchmark of failure scenarios.

### Planned Approach

My approach draws from concepts learned in Topic 1 and 2. RQ1 will follow this pipeline that will be applied to two variants: zero-shot and few-shot, among 1-2 different LLMs:

0. For each nominal problem file, generate a nominal plan with a numeric planner (e.g., ENHSP or Metric-FF), and use VAL to confirm that it is valid on the nominal problem file. The nominal plan succeeds on the nominal problem by construction.
1. The LLM will be prompted following Liu et al.'s techniques to generate problem files that target different failure modes [3]. Each problem file generated will be a perturbation of a baseline nominal problem file, for each category of failure. The failure categories, and how each one is expressed in a Rovers problem file:

   | Failure category (anomaly) | Example perturbation of the nominal problem file |
   | --- | --- |
   | Displaced object | Move `at_soil_sample` / `at_rock_sample` to a different waypoint |
   | Terrain hazard / blocked path | Remove a `can_traverse` fact |
   | Power loss | Lower a rover's initial `energy`, or remove `in_sun` from a waypoint |
   | Communication loss | Remove `visible` facts between waypoints and the lander's waypoint |
   | Equipment fault | Remove an `equipped_for_…`, `on_board` or `calibration_target` fact |

   Check these predicate and function names against the actual domain file before using them.
2. These perturbed problem files will be coupled with the Rovers domain and the nominal plan, in order to check whether the nominal plan still holds in the perturbed world.
3. Use a plan validation tool, VAL, to verify that the nominal plan, when validated against the perturbed problem file, encounters the intended failure mode (i.e., that there is misalignment when compared to the nominal problem) [2]. Record the step, action and unsatisfied precondition at which VAL first reports a failure.

**Definitions used by the pipeline:**

- **Nominal problem / nominal plan:** the original, unperturbed problem file, and a plan that VAL confirms is valid on it.
- **Perturbed problem:** a copy of the nominal problem file in which the LLM changed the initial state to inject one anomaly. In RQ1, "plans" means the nominal plan, validated against the perturbed problem.
- **Valid perturbation:** the perturbed problem file parses, is well-formed against the domain (types and objects are consistent), and keeps the goals of the nominal problem file.
- **Failure:** VAL rejects the nominal plan on the perturbed problem file.
- **Non-trivial failure:** the perturbation is small (only a few initial-state facts or fluent values change), does not simply delete a goal or an object, and the action at which VAL first fails is consistent with the requested failure category.

RQ2 will be explored via analysis of the differences between the generated and nominal problem files:

1. Compare the diff between the problem files.
2. Find the non-trivial features (i.e., changes made to the nominal file that actually caused the nominal plan to fail).
3. Mine patterns across the different problems with the information we have (non-trivial changes, failure mode, failing actions, information from VAL, etc.).
4. Run the planner on each perturbed problem file to record whether a new plan still exists (recoverable) or not (unrecoverable). This distinguishes instantiations that should be avoided from those that can be planned for.

### Evaluation

To evaluate whether my approach is successful, I will use a variety of metrics to assess the performance of my proposed method. RQ1's metrics will include measuring valid perturbed problem files generated by the chosen LLM(s), the rate at which they cause the nominal plan to fail, non-triviality of the problem files/failures, agreement between the requested and observed failure category, diversity of anomalies, and metrics that compare the different inference techniques (zero-shot vs. few-shot). RQ2 will be evaluated via a table that ranks features by how much they contribute to the failures. Additionally, I hope to look into non-trivial features that cause the greatest errors. The table will also note whether the failures each feature causes are recoverable by replanning. These metrics matter, as a clear list of correlated features to failures will aid in preparing against foreseeable errors.

### Changes from the Milestone 1 proposal (for plan.tex)

The Milestone 2 report must state any changes from the proposal and the reason for each. These are the changes:

- **RQs:** RQ1 and RQ2 were revised to the wording above. RQ1 now uses an existing domain and asks about perturbed problem files. RQ2 now asks about patterns in the perturbations and about problem-file instantiations (initial-state configurations), in response to instructor feedback asking what "configurations" meant.
- **Domain:** the proposal planned to extend the Rovers domain with lunar actions and anomaly predicates. Building and validating that domain is not feasible in the project's time frame, so the existing Rovers domain is used as-is and anomalies are injected through the problem files instead. The lunar domain is future work.
- **Fine-tuning:** dropped, because of the time frame and the lack of training data for this specific domain. Only zero-shot and few-shot prompting are compared. The fine-tuning corpus (IPC problem files from Satellite, Depots and Logistics) is therefore no longer used.
